# ADR-001 · Backend for Frontend (BFF) propio

**Problema.** La app necesita combinar datos de varios dominios (cuentas, personalización, notificaciones, terceros), adaptar respuestas al móvil y aislar a la app de cambios en los sistemas internos. Llamar directamente a cada servicio desde el teléfono acopla la app a N contratos, multiplica la latencia en redes móviles y expone superficie de ataque.

**Alternativas evaluadas.**
1. App → servicios/core directamente.
2. API Gateway genérico (Kong/Apigee) sin lógica de experiencia.
3. GraphQL federado.
4. **BFF dedicado al canal móvil (Node.js + Express).**

**Decisión.** Opción 4. Un BFF que agrega, adapta y aplica políticas propias del canal: armado de la experiencia (SDUI), idempotencia, tokens de micro-apps, circuit breaker hacia terceros y fault injection para QA.

**Trade-offs.**
- (+) La app habla un solo contrato estable. La lógica de experiencia evoluciona sin publicar la app. Las políticas de seguridad quedan centralizadas.
- (−) Es una pieza más que operar y escalar, y existe el riesgo de que el BFF crezca como "monolito de canal".
- (−) GraphQL daría más flexibilidad de consulta, pero agrega complejidad de caché, de seguridad (consultas costosas) y de tooling para un MVP.

**Impacto a largo plazo.** El BFF es dueño del canal, no del negocio: el saldo real vive en el core. Cuando crezcan los equipos, el BFF se divide por dominio (BFF de cuentas, de personalización…) detrás de un gateway, sin que la app cambie, porque los paths ya están agrupados por dominio (`/v1/accounts`, `/v1/experience`…). Para la prueba, SQLite simula el core. En producción, los repositorios del BFF se reemplazan por adaptadores al core bancario (p. ej. API REST del core o BIAN).
